# AAR 复盘 / After Action Review

## 一、预期 vs 实际

| | 计划 | 实际 |
|---|---|---|
| 时间分配 | 读代码 20%，写转换器 50%，写文档 30% | 读代码 10%，写转换器 45%，**调 bug 25%**，文档 20% |
| 新增能力 | 从清单里挑 2–3 项 | 清单上 10 项全部做完，另加校验器和评测器 |
| 最难的部分 | 以为是把公式渲染成 PNG | 实际是**验证「到底什么会坏」** |
| 最大的意外 | — | 校验器抓出的问题里，有一半是我自己写的 bug |
| 未完成 | — | **真实发布**——我没有用户的公众号凭证，只能准备到「一粘贴即发布」 |

一句话总结：**写代码比预期容易，确定「代码对不对」比预期难十倍。**

## 二、做对了什么

### 1. 先建校验器，再写功能

我在写转换逻辑之前先写了 `wechat_validate.py`。这个顺序决定了后面所有事：
每加一个能力，立刻能知道它有没有把输出弄坏。

如果反过来，等全部写完再验证，我大概会在「看起来没问题」的状态下交付一个
有五个静默 bug 的东西——因为这些 bug 全都不报错。

**证据**：`no_markdown_leftovers` 这条检查抓到了我自己写的 callout bug（见下），
那时候距离我写完那段代码还不到十分钟。

### 2. 用「有技能 vs 无技能」做对照，而不是自我评价

`run_eval.py` 的基线是「不用技能、老老实实写个脚本转」，结果 4/19。
这个数字不是装饰——它把「这个技能到底加了什么价值」从主观判断变成了可复现的对照。

### 3. 第一个 bug 就回头改设计，而不是打补丁

`<div>` → `<p>` 的朴素改名会产生 `<p><table>` 这种非法嵌套。我没有加一个
「遇到 table 就跳过」的特判，而是加了通用的 `split_nested_blocks()`，
把任何 `<p>` 里的块级子元素都提出来。后面 Word 输入又踩到同一个问题，
这次不需要改代码。

## 三、失败记录

这是这份复盘里最有用的部分。以下每一条都是真实发生的，不是假设。

### 失败 1：九個提示框，只有四个渲染出来

**现象**：让校验器跑第一篇测试文章，报告 `no_markdown_leftovers` 失败，
残留 `{WARNING, DANGER, KEY, SUCCESS}`。

**排查**：先怀疑正则写错，检查后发现正则没问题。真正的原因要用代码验证——
把 Markdown 中间产物打出来看：

```
blockquote count: 4
  bq0: 1 p(s)
  bq1: 6 p(s)     ← 六个提示框被合并成一个 blockquote
  bq2: 1 p(s)
  bq3: 1 p(s)
```

**根因**：Markdown 会把**连续的引用块合并成同一个 `<blockquote>`**，
九个提示框进去，出来是「一个元素里的九个段落」。我的实现只处理了
`bq.find("p")` 的第一个段落，剩下五个原样留在了正文里。

**修法**：改成扫描 blockquote 里**每一个**顶层段落，遇到 `[!TYPE]` 就开一个新框，
后续段落归入当前框。切分成「run」再逐个生成。

**教训**：我假设了「一个 blockquote = 一个提示框」。这个假设在日常写作里
大部分时候成立，所以很容易一直不知道它是错的。**唯一的发现途径是自动校验。**

### 失败 2：`'NoneType' object is not callable`

**现象**：`soup.new_tag(...)` 抛 `TypeError: 'NoneType' object is not callable`。

**排查**：这行代码本身没问题，问题在 `soup` 上。我传进去的其实是一个
`Tag`（`<body>`），不是 `BeautifulSoup` 实例。

**根因**：bs4 的 `Tag` **没有** `new_tag` 方法，但它定义了 `__getattr__` 用来
查找子标签。所以 `body.new_tag` 不会抛 `AttributeError`，而是返回
「名为 `new_tag` 的子标签」—— 这里是 `None`。然后 `None(...)` 就报了
一个完全指向别处的错误。

**修法**：先用 lxml 解析以获得容错，再取出 body 内容重新解析成一个扁平
`BeautifulSoup` 对象，全程只用一个对象。

**教训**：属性查找被重载的库会把错误信息搬到离原因很远的地方。
遇到「莫名其妙的 NoneType」，先看**接收者**是什么，而不是看参数。

### 失败 3：`argparse` 把输出路径当成第二个输入

**现象**：`convert.py in.md out.html` 报「多个输入时必须指定 --outdir」。
更糟的是，这条错误信息把人引向了错误的方向——用户会以为是输入写错了。

**根因**：`nargs="*"` 的 positional 后面跟 `nargs="?"` 的 positional，
`*` 会把两个路径都吃掉，`output` 永远是 `None`。这是 argparse 的已知行为。

**修法**：只声明一个 `nargs="*"` 的 `paths`，用 `split_paths()` 约定
「正好两个路径时，最后一个是输出」。同时在 `--help` 里写明这个约定。

**教训**：**错误信息也是一种产品界面。** 我第一版的错误信息不仅没帮上忙，
还指错了方向。修完之后，同样的情况下用户看到的是能直接照做的一句话。

### 失败 4：`\displaystyle` 让公式渲染全灭

**现象**：两个独立成行的公式渲染失败，报
`ParseFatalException: Unknown symbol: \displaystyle`。

**根因**：我为了「让行间公式更正式」在渲染前加了 `\displaystyle` 前缀，
但 matplotlib 的 mathtext **不支持这个宏**，而且我的兼容层 `_COMPAT` 是在
加前缀**之前**跑的，所以清理不掉。

**修法**：去掉这个前缀。mathtext 本来就不区分行内/行间样式，
「行间公式更大」应该由**图片的显示尺寸**实现，而不是由 TeX 源码实现。

**教训**：兼容层的位置决定了它能兼容什么。我把「清理不支持的宏」放在了
「添加自己的宏」之前——顺序反了，而且这个顺序错误不会立刻暴露。

### 失败 5：公式字号忽大忽小

**现象**：截图对比发现，短公式的字明显比长公式小。

**根因**：我按**图片高度**等比缩放。但 matplotlib 是按固定比例把字号烘焙进
像素的（磅 × dpi），图片高度只说明**公式有多高**，不说明**字有多大**。
一个带 `\sum` 上限的短公式，图片很高，按高度缩放后字就变小了。

**修法**：改用**固定比例** `scale = 正文字号px / (pt/72 × dpi)`。
所有公式的字号因此一致，与公式本身的高矮无关。行间公式再统一放大 1.25 倍。

**教训**：看起来正确的公式（按高度等比缩放）在**单张**图片上永远是对的，
只有把两张放一起才看得出问题。**视觉缺陷需要对比才能发现**，
这也是我坚持截图检查而不是只看 HTML 的原因。

### 失败 6：校验器自己误报

**现象**：样例文章校验失败，`no_markdown_leftovers` 报残留 `[!TIP]`。

**排查**：那篇文章里有一句「写 `[!TIP] 自定义标题` 就能覆盖默认标题」——
`[!TIP]` 出现在**行内代码里，是文档内容**，不是没转换成功的标记。

**修法**：把这条检查从「全文正则」改成**结构化判断**：
只看段落**开头**是不是 `[!TYPE]`（没转换成功的提示框一定在段首），
比较前先把等宽字体的 `<span>` 去掉（那是代码，不是正文）。

**教训**：一个会误报的校验器比没有校验器更坏——它会训练人忽略它。
判据必须建立在「失败长什么样」这个结构性事实上，而不是关键词上。

### 失败 7：评测在测一套和用户不一样的配置

**现象**：`toc_generated` 这条断言失败，但那篇文章的 front matter 里写着
`toc: always`。

**根因**：`run_eval.py` 直接用 `Options(toc="auto")` 调渲染函数，
**完全没读 front matter**。而命令行工具是读的。也就是说：
评测在验证一套用户永远不会遇到的配置。

**修法**：把 front matter 的解析和类型转换从 CLI 里抽出来，放进
`render.py` 的 `front_matter_options()`，CLI 和评测器共用同一个函数。

**教训**：**评测路径和生产路径必须共用代码，否则评测是自欺欺人。**
这是我最想留给后来者的一条：只要有两份「怎么读配置」的实现，
它们一定会漂移。

### 失败 8：评测因为 HTML 转义而误判

**现象**：`code_lines_preserved` 失败，报告少了一行
`return [r for score, r in sorted(scored, reverse=True) if score > 0]`。

**根因**：源码里的 `>` 在 HTML 里是 `&gt;`。我的比较逻辑先去标签、
再比字符串，但没有反转义，所以永远比不中。

**修法**：加 `html.unescape()`。

**教训**：和失败 2 同源——**比较两个世界的字符串之前，先确认它们在同一个世界里。**
一个是 Markdown 源码，一个是 HTML 文本，中间隔着转义这一层。

### 失败 9：Windows 上的 UTF-8 连环坑

**现象与处理**：

| 现象 | 原因 | 处理 |
|---|---|---|
| 中文文件名读不出来 / mojibake | Python 在 Windows 默认用 GBK 打开文件 | 所有读写显式传 `encoding="utf-8"`；读源码依次尝试 utf-8-sig → utf-8 → gb18030 → big5 |
| 控制台打印中文报 `UnicodeEncodeError` | 控制台编码是 GBK | 命令前加 `PYTHONIOENCODING=utf-8` |
| `skill-creator` 的校验脚本崩溃 | 它用 `read_text()` 没指定编码 | 加 `PYTHONUTF8=1` 绕过 |

**教训**：中文环境下的工具链默认值大多对中文不友好。这不是「可选优化」，
是必须处理的**平台差异**——我在 `read_text()` 里做的多编码回退，
就是照着「用户手上的文件来自 Word、来自微信、来自各种年代」这个现实写的。

### 失败 10：图标画不出来

**现象**：生成的图里 ✓ 和 ✗ 显示成空心方框。

**根因**：Windows 中文字体（微软雅黑）没有 U+2713 / U+2717 的字形。

**修法**：换用 U+221A（√）和 U+00D7（×），这两个在 CJK 字体里一定有。
顺带加了字体回退链。

**教训**：**渲染出来的东西要真的看一眼。** 这个 bug 在代码层面完全无法发现，
只有看图才知道。

### 失败 11：skill-creator 拒绝了我的描述

**现象**：`quick_validate.py` 报 `Description is too long (1179 characters). Maximum is 1024.`

**处理**：把描述从 1179 字符压到 992 字符，删掉重复的表达，保留全部触发场景。

**教训**：这不是找麻烦——技能的 description 是**每次会话都会进入上下文**的元数据
（渐进披露的第一层）。约束本身在提醒：这一层应该是「什么时候用我」，
而不是「我有多能干」。

### 失败 12：把「去掉中文前缀」执行成了「去掉中文」，导致两个必交件被判缺失

**现象**：交付物全部完成、内容齐全、校验 14/14 通过，但平台判定
`文章链接` 和 `AI日志` 两项 **missing**。

**根因**：用户的要求是「统一文件命名（**去除中文前缀**或提供英文别名）」。
我把这句话理解成「文件名尽量英文化」，于是把描述部分也一起翻译了：

```
songpengfei_C4B_article_link.md   ← 实际产出
songpengfei_C4B_AI日志.md          ← 平台需要中文子串
```

而 EduSeed 平台按**文件名里的中文子串**判定必交件是否齐全
（`challenge.json` 的 `required_deliverables` 写着
`*wechat-publisher*,*文章链接*,*AI日志*`）。
结果就是：文件名里不含 `文章链接`，内容再全也判缺失。

**为什么没早发现**：整个开发过程里我一次都没有运行过「平台的判定逻辑」。
我验证了转换正确、校验通过、评测达标、技能能装能跑——**唯独没有验证
「平台能不能认出这是它要的东西」**。这是验证覆盖面上的一整块盲区，
不是某一条断言的疏漏。

用户做了两组对照探针，把根因钉死在命名上：`文章链接` 那篇的**正文**里
明确写着「公众号文章链接」，照样被判缺失——说明匹配只看文件名，不看内容。

**修法**：`姓名` 部分用拼音（这正是「去除中文前缀」要处理的部分），
**描述部分逐字保留挑战原文的中文用词**。

**教训**：

1. **「去掉中文前缀」的范围是前缀，不是全部中文。** 我把一条缩小范围的指令
   执行成了扩大范围的改动。指令里出现「或」的时候，应该先确认两个选项的
   取舍标准，而不是挑自己顺手的那个。
2. **交付物的验收标准不只来自文档，还来自那个会检查它的程序。**
   `CHALLENGE.md` 的命名表格我读过了、也照做了一半——但我从没想过
   「有没有一个程序在读这些文件名」。存在自动判定的地方，就该把判定本身
   复现成一条自查命令，而不是靠肉眼比对表格。
3. 修完之后我把「复现平台三项判定」的脚本写进了 README，并更新了记忆——
   否则下一个挑战会一模一样地再犯一次。

### 失败 13：发布出来了，但没有任何检查看过「线上到底是什么样」

**现象**：文章成功发布、链接可访问，但线上正文是 **Markdown 源码**——
`---`、`title:`、`##`、`**`、未转换的 `[!NOTE]` 全部原样显示，标题栏还是占位符。

**根因**：粘贴时复制的是**源文件 `.md`**，不是渲染后的预览页 `.html`。
浏览器把 `.md` 当纯文本渲染，所以 Ctrl+A 复制到的就是原始 Markdown。

**为什么整条流水线都没拦住**：

| 检查 | 覆盖到哪 | 能发现这个吗 |
|---|---|---|
| `wechat_validate.py`（14 项） | 转换产物 | ❌ 产物是好的 |
| `run_eval.py`（25 条断言） | 转换流水线 | ❌ 流水线没问题 |
| 浏览器预览 | 你眼前那一页 | ⚠️ 只有你打开的是**对的那一页**才能发现 |
| 线上核验 | 已发布的页面 | ✅ 只有它能发现 |

**这次失败的形状**和前面 12 条都不一样：
前 12 条都是「我产出的东西有缺陷」，
**这一条是「我产出的东西没缺陷，但交付出去的不是它」**。

**教训**：

1. **验证必须覆盖到最终交付形态。** 我验证了文件、验证了流水线、验证了技能能装能跑，
   唯独没验证过**读者看到的那一页**。交付链路只要有一环没被观测，
   那一环就能静默出错——这和第 7 条（评测路径与生产路径必须共用代码）是同一个道理，
   只是这次的「生产路径」延伸到了平台外面。
2. **人机交界处是最脆弱的一环。** 粘贴这一步既不属于我的代码，也不属于平台的自动化，
   它落在人手上，因此没有任何自动检查覆盖。凡是这种地方，就该补一个**事后核验**，
   而不是指望「下次注意」。
3. 修法不是叮嘱，是工具：新增 `scripts/check_published.py`，
   抓取线上页面、判断正文是渲染后的 HTML 还是残留的 Markdown，
   非零退出码。它十分钟写完，而这次失误花了远不止十分钟。
   现在它被写进了发布 SOP 的第 10 步（必做）。

### 失败 14：我新写的核验工具，自己重犯了失败 6

**现象**：`check_published.py` 第一次跑线上文章，报「`[!NOTE]` 残留 3 处」。
但线上文章其实是对的——那 3 处全在**行内代码里**，是文章在讲「这个语法怎么写」，
属于正常的文档内容。

**根因**：扫描前没有剔除等宽字体的代码片段。

**为什么值得单独记一笔**：这正是我在**失败 6** 里已经写下的教训——

> 一个会误报的校验器比没有校验器更坏，它会训练人忽略它。

我写下了这条，然后在**同一个月内新建的工具里又犯了一次**。
写下教训和把教训变成代码，是两回事。

**修法**：扫描前先剔除 `<span style="…monospace…">` 内容。这个修法是安全的：
如果粘贴的是 Markdown 源码，页面上根本不会有等宽样式，也就没有代码片段可供「藏身」。
同时补了 `--expect-title`，把「标题栏填错」这个第二类失败也纳入覆盖——
它正是在这次核验里被抓出来的。

**教训**：**校验器的误报率是它的可用性上限。** 一个只会说「对」的工具没人看，
一个时不时报假警的工具同样没人看。写断言的时候要问的不是「这能不能检出问题」，
而是「它会不会把正确的东西判成错的」。

## 四、如果重来一次，会怎么做

1. **先写校验器**——这次做对了，会继续。
2. **更早把「从 Markdown 到中间 HTML」打出来看**。失败 1 花了很久才定位，
   因为我一直在看最终的 HTML，没看中间产物。以后再遇到「转换结果不对」，
   第一步就是把流水线每一步的中间结果 dump 出来。
3. **配置读取只允许一处实现**。失败 7 的根因是两处实现，这个原则值得推广到
   所有「多个入口读同一份配置」的场景。
4. **每写完一个能力就截图**。失败 5 和 10 都是纯视觉问题，
   如果我在每个能力写完时就截一次图，两个都会当场发现，而不是攒到最后。
5. **给测试用例加上「已知脏数据」**。我的三个用例里只有一个是脏的
   （Word 粘贴出来的 HTML），另外两个都太干净。真实用户的文档更脏。

## 五、对「AI-First」这件事的认识

**AI 在这里最大的作用不是写代码，是试错。**

四千多行代码里，真正难的不是算法——是那十四条失败记录。而它们的共同点是：
**都不会报错**。静默失败、看起来对、只在特定条件下错。

发现这类问题需要的是「提出假设 → 写一个能证伪的测试 → 跑 → 看结果」这个循环。
AI 让这个循环的成本降到几乎为零——我可以在一次对话里试五个假设。
但**提出哪个假设**仍然需要人来判断：是「Markdown 合并了引用块」还是
「我的正则写错了」，这个方向感来自对系统的理解，不来自模型。

所以这次的分工其实是：

- **我负责**：定义规则、判断哪个假设值得试、决定什么算「对」、读图看结果。
- **AI 负责**：把假设快速变成可运行的验证、把结论固化成代码和检查。

规则一旦被写下来就变成资产。这篇文章、这个技能、这套校验器，
都是同一件事的不同形态：**把踩过的坑变成别人不用再踩的路。**
