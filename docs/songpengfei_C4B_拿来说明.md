# 拿来说明 / What I took from the starter kit

挑战要求「拿来主义」：不是从零写，而是理解已有工具、改造它、超越它。这份文档把
每一处改动都摆出来——拿了什么、改了什么、为什么改。

> 对照基准：`materials/c4b-wechat-publisher-starter.zip`
> （383 行脚本 + 144 行 SKILL.md + 192 行 reference = 719 行）
> 产出：`skill/wechat-publisher-pro/`（4565 行脚本 + 200 行 SKILL.md + 730 行 reference = 5500 行）

## 二、原样保留的部分

这些是 starter 做对了的地方，我没有动：

1. **标签白名单的内容**。`p, h2, h3, ul, ol, li, span, img, a, table, tr, th, td, br`
   这份清单是准确的，我把它原样搬进了 `render.py` 的 `ALLOWED_TAGS`。
2. **「不覆盖已有 style」的原则**。starter 的 `apply_styles()` 里有一句
   `if existing: continue`，注释写着「不要覆盖手工设置的样式」。这个判断是对的，
   我保留了同样的语义——只是现在由各个阶段显式设置样式，而不是靠跳过实现。
3. **「摘要 + 分步命令 + 使用示例」的 SKILL.md 骨架**。我的 SKILL.md 仍然是这个结构。
4. **示例文章的存在本身**。starter 用小样例证明「能跑通」，这个思路我保留了，
   只是把样例从「证明能跑」升级成「把所有能力都用一遍」。

## 三、改掉的部分，以及为什么

### 1. 代码块：从「一个段落」改成「一行一段落」

**starter 的做法**（`convert_to_wechat.py` 的 `sanitize()`）：

```python
p = soup.new_tag('p')
p.string = code_text          # 整段代码，含换行符
p['style'] = STYLES['code_block']
pre.replace_with(p)
```

**问题**：HTML 会折叠文本里的换行符。这段话在浏览器里看着没问题——因为浏览器
把 `\n` 渲染成一个空格，多处换行看起来像「挤在一起」；但粘进公众号之后，
整段代码会塌成**一行**。这是一个只在真实发布时才暴露的 bug。

**改法**：每一行代码是独立的 `<p>`，整块包在一个单元格里，由单元格的背景色
负责视觉上的整体感（`render.py` 的 `convert_code_blocks()`）。

### 2. `<div>` → `<p>`：从直接改名改成按内容判断

**starter 的做法**：

```python
for div in soup.find_all('div'):
    div.name = 'p'
```

**问题**：如果 `<div>` 里装的是表格或列表，改名之后会变成 `<p><table>...</table></p>`。
`<p>` 不能包含块级元素，公众号渲染这种结构的表现不稳定——有时表格消失，有时
段落的行高把整个表格撑变形。

**改法**：分两步。`split_nested_blocks()` 把块级子元素提到 `<p>` 外面；
剩余的非白名单标签在清理阶段 `unwrap()`（保留内容、去掉标签）。

### 3. 引用块：从「取纯文本」改成「保留内部结构」

**starter 的做法**：

```python
p.string = bq.get_text()      # 丢掉内部的加粗、行内代码、链接
```

**问题**：`get_text()` 会把引用块里的 `**加粗**` 和 `` `代码` `` 全部拍平成纯文本。

**改法**：把引用块的子节点搬进新的 `<p>`，内部的 `<span>` 原样保留；
如果引用块里有列表，把列表提出来作为兄弟节点（`convert_blockquotes()`）。

### 4. Word 读取：从「只走段落」改成「按文档顺序走」

**starter 的做法**：

```python
for para in doc.paragraphs:   # 只遍历段落
```

**问题**：`doc.paragraphs` 只返回段落，**表格和图片全部丢失**。一个带数据表的报告
转出来会少掉整张表，而且不会报错。

**改法**：遍历 `document.element.body`，按真实顺序处理段落、表格、图片
（`converters.py` 的 `read_docx()`）。表格转成 `<table>`，内嵌图片从文档包里
提取出来转成 base64。顺带补上了列表样式和删除线。

### 5. 依赖安装：从「静默 pip install」改成「打印命令，用户决定」

**starter 的做法**：`install_dependencies()` 在导入时就检查并自动安装，
命令行里还带着 `--break-system-packages`。

**问题**：一个转换脚本在启动时修改你的 Python 环境，这件事本身就不该默认发生。
在受管环境里它会以很难懂的方式失败，在个人机器上它会装你不想要的东西。

**改法**：`check_dependencies()` 只检查并打印**这一台机器上**该跑的准确命令
（用 `sys.executable`，不是裸 `python`）。想让它代劳就加 `--install-missing`。
顺带把可选依赖（matplotlib、pygments）也报出来，让「公式降级为文本」这类
现象在运行前就有解释。

### 6. CSS 白名单：从「只列允许的」改成「允许 + 明确禁止」

**starter 的做法**：只有一个 `ALLOWED_CSS` 集合。

**问题**：判断一个属性是否安全，和知道它会被剥掉，是两种不同的知识。
`box-shadow` 不在允许列表里，但作者看到它「被静默移除」和看到
「已移除 3 条公众号不支持的声明（定位/动画/阴影等）」是两种体验。

**改法**：拆成 `ALLOWED_CSS_PROPS` 与 `FORBIDDEN_CSS_PROPS`，并统计被丢弃的
声明数量、在运行结果里报告出来。这样浏览器预览里看到的，就是发布后能留下的。

### 7. 样式表：从「写死的字典」改成「从调色板推导」

**starter 的做法**：`STYLES = {...}`，每个元素一条写死的字符串，
注释里写着「这是最容易定制的地方」。

**问题**：想换主题就得改 20 多个字符串，而且很容易改漏——比如把主色改了，
却忘了表格表头还指着旧颜色。

**改法**：`themes.py` 里定义调色板 token，`build_styles()` 从调色板推导出全部
样式。改一个 `accent`，标题色条、表格表头、引用边框、目录底纹会一起变。
六套内置主题因此只需要各写 20 个色值，而不是各写 300 行 CSS。

## 四、新增的能力

starter 的 SKILL.md 里列了一张「缺少的能力，是你的机会」的表。逐条对照：

| starter 列出的缺口 | 状态 | 实现位置 |
|---|---|---|
| 主题 / 配色系统 | ✅ | `themes.py`，六套主题 + 自定义 JSON + `--accent` 单色覆盖 |
| 数学公式 | ✅ | `mathpng.py`，LaTeX → base64 PNG，含 Unicode 降级 |
| 图片处理 | ✅ | 本地图片转 base64、alt 转图注、缺图给可视化提示 |
| 文章元数据 | ✅ | front matter → 署名行 + 摘要框 + `<title>` |
| 目录生成 | ✅ | 自动生成，故意不给锚点链接（公众号会剥掉 `id`） |
| callout / 高亮框 | ✅ | 9 种类型，`> [!NOTE] 标题` 语法 |
| 页脚 / 版权信息 | ✅ | 按作者名生成，可用 front matter 覆盖 |
| 中文排版优化 | ✅ | `typography.py`，中英文间距 + 标点规范化 |
| 多语言支持 | ✅ | 中英混排间距；编码依次尝试 utf-8/gb18030/big5 |
| 批量转换 | ✅ | `--outdir` + 通配符输入 |

starter 没列出、但我认为同样重要的三项：

- **合规校验器**（`wechat_validate.py`）：14 项检查，每项对应编辑器的一个真实行为。
  「预览好看」不是证据，这是让「能用」变成可验证的关键。
- **多平台导出**（`--also zhihu,plain`）：一稿多投是真实需求，知乎版和纯文本版
  可以从同一份源文件生成。
- **评测工具**（`run_eval.py`）：用「有技能 vs 无技能」做对照，把「好用」量化。
  这是判断改动是否真的更好的唯一办法。

## 五、没有做的部分

诚实说明边界：

1. **没有做公众号 API 自动发布。** 那需要 AppID / AppSecret 和服务器 IP 白名单，
   属于账号所有者的凭证。技能停在「生成可粘贴的 HTML」，最后一步仍然是人来点。
   这是刻意的边界，不是遗漏——一个技能不该向你索要账号密钥。
2. **没有做横向滚动的代码块。** 公众号没有这个能力，超长行只能折行。
   这是平台边界，写进了提示信息而不是假装解决了。
3. **仍然不支持 callout 里嵌代码块。** Markdown 会把引用块里的围栏代码块拍平，
   要支持得自己写 Markdown 扩展。收益不大，先记在 SKILL.md 的限制里。
4. **starter 的 `examples/sample_output.html` 没有沿用。** 它是旧脚本的产物，
   留着会造成「两个事实来源」的困惑。改为由新脚本重新生成，并在
   `examples/sample_article.md` 里放一份把所有能力都用一遍的样例。

## 六、一句话总结

starter 给了**骨架**（读文件 → 净化 → 施加样式 → 输出），
我补的是**判断力**：知道公众号在哪一步会静默吃掉什么，然后把每一条都变成
代码里的一个显式决策，以及校验里的一个断言。
