一切都从那次粘贴开始

上周我把写好的一篇稿子从 Word 粘进公众号编辑器。

标题字号变了，代码框没了，表格的边框全消失，两张图只剩占位符。然后我花了四十分钟手工调——调完手机上一看，还是不对。

那天晚上我想明白一件事：我不是在写文章，我是在给一个坏掉的编辑器做适配。

于是我把它做成了一个技能。现在流程是：

bash

python scripts/convert_to_wechat.py article.md out.html

打开 out.html，全选复制，粘进编辑器，发。

🔑 重点 · 核心

输入 Markdown 或 Word，输出可以直接粘贴的公众号 HTML。一句话说不清输入输出的工具，都还不够聚焦。

公众号编辑器到底会丢掉什么

这是整件事的地基，值得单独说。下面每一条都不会报错，你只会在发布之后才发现。

公众号编辑器在粘贴时静默丢弃的东西

其中最要命的是两条：

第一，class 会被保留但永远不生效。 编辑器里根本没有样式表，class="title" 只是一个没人读的标签。所以每一个样式都必须写在元素自己的 style 属性里。

第二，SVG 会在保存那一刻消失。 这条最隐蔽——你在浏览器里预览得好好的，点保存，图没了。因为公众号要把图片重新上传到自己的图库，而它不认识 SVG。

⚠️ 注意 · 一个反直觉的结论

你以为对手是「编辑器不好用」，其实对手是「编辑器有一套你没被告知的规则」。搞清楚规则，问题就从设计问题变成了工程问题。

为什么不能手工调

手工调格式的真正问题不是慢，是不可复用。

同一套样式，第二篇文章要重来一遍；改了主色，二十个小标题要一个个改；发到知乎要重排一次。每一次都是纯体力劳动，且每次都会漏。

所以正确的做法是把它当成一次转换：

python

# 输入：Markdown 或 .docx

# 输出：公众号可粘贴 HTML

options = Options(theme="accent", toc="always")

preview, fragment, report, meta = render_document(source, options)

主题、目录、callout、公式、字号，全都变成参数。改一个 --theme ink，标题色条、表格表头、引用底色、目录底纹会一起变——因为它们指向同一个色值。

三个真的坑，都是在测试里才暴露的

写代码不难，难的是知道什么会错。这三个是我在真实测试里撞出来的：

坑一：连续的提示框会被 Markdown 合并成一个

我写了九个提示框，转换后只有四个渲染成功，另外五个变成了正文里的 [!WARNING] 字样。

原因是 Markdown 会把连续的引用块合并成同一个 <blockquote>，九个提示框进去，出来是一个元素里的九个段落。我第一版代码只处理了第一个段落，剩下的全漏了。

修法是把 blockquote 里每一个顶层段落都当成一个可能的提示框起点，切成若干段分别处理。

🚨 警告 · 这类 bug 的特点

不报错、不崩溃，只是少了东西。如果不做自动校验，我大概率会在发布之后才发现文章里躺着五个 [!NOTE]。

坑二：代码块会被公众号压成一行

第一版把整段代码塞进一个 <p> 里，靠换行符分行。浏览器里看着没问题，粘进公众号之后，换行符被折叠了，五十行代码变成一行。

修法是每一行代码单独一个段落，整块包在一个单元格里——单元格的背景色负责让它看起来还是一个整体。

坑三：公式只能以 PNG 的形式活着

公众号不支持 MathML，不支持 KaTeX，还会丢掉内联 SVG。唯一能在「粘贴 → 保存 → 发布」全流程活下来的载体，是 base64 编码的 PNG。

但这里还有个二阶问题：matplotlib 渲染出来的图片尺寸各不相同，如果按图片高度去缩放，长公式和短公式的字号就不一样了。正确的做法是按固定的比例缩放——因为图片的每磅像素数是固定的，图片高度只说明公式有多高，不说明字有多大。

怎么确认它真的能用

「我预览过了，没问题」不是证据。浏览器里好看、发布后崩掉，恰恰是这类工具最常见的失败方式。

所以我写了 14 项自动校验，每一条都对应编辑器的一个真实行为，并且会指出具体是哪个元素有问题：

检查项 拦下的是什么
no_forbidden_tags script / style / div / pre 残留
inline_styles_present 块级元素漏了 inline style
css_props_supported 用了公众号会剥掉的定位、动画、阴影
no_markdown_leftovers 没转换成功的 **、[]()、[!NOTE]
images_embedded_or_remote_flagged SVG、空地址、远程图片

然后我拿三个真实场景做了对照测试：同一个任务，一个用技能、一个不用技能（不用技能就是我自己写脚本硬转）。

场景 用技能 手工写脚本
带代码块的教程 8/8 2/8
带公式的统计文 7/7 1/7
Word 粘出来的脏 HTML 10/10 1/10
合计 25/25 4/25

差距不在「能不能转」，而在知不知道会错在哪。

✅ 结论

一个技能真正的价值，不是替你干活，是替你记住那些踩过的坑。

怎么用

装依赖：

bash

python -m pip install markdown beautifulsoup4 lxml python-docx

python -m pip install matplotlib pygments # 可选：公式与代码高亮

转换：

bash

python scripts/convert_to_wechat.py article.md out.html --theme accent --validate

看有哪些主题：

bash

python scripts/convert_to_wechat.py --list-themes

六套主题：中性灰蓝、蓝调、暖阳、极简、终端、墨韵。写技术文用蓝调或终端，写随笔用暖阳或墨韵。

仓库里的 examples/sample_article.md 把所有能力都用了一遍——主题、九种提示框、公式、代码高亮、目录、图注。它能干净地转出来，说明环境是通的。

一点感想

这件事最反直觉的地方在于：我花在「搞清楚规则」上的时间，远多于写代码的时间。

代码本身不复杂，四千多行 Python 里有一大半是在处理边界情况和报错提示。真正难的是先去把那些没人写下来的规则一条条试出来——哪些标签会没、哪些属性会被剥、哪个环节会静默失败。

AI 在这里的作用不是替我写代码，而是替我试错。每一条规则我都让它给出假设、写出验证用例、跑一遍看结果，然后再把结论固化进校验里。

规则一旦被写下来，就变成了资产。下次写任何一篇文章，一条命令，出稿。
