# session_notes — Markdown → 公众号 HTML

任务：把 `skill/wechat-publisher-pro/evals/cases/tutorial_with_code.md`
排成可以直接粘进 mp.weixin.qq.com 正文编辑器、手机上看着舒服的 HTML。
没有现成工具或技能，自己写了个 Python 脚本。

耗时：约 12 分钟（读源文件 → 写转换器 → 生成 → 自查 → 修 bug → 复验）。

## 产出

| 文件 | 说明 |
|---|---|
| `tutorial_with_code.html` | 成品，9.8 KB，双击用浏览器打开 |
| `convert.py` | 转换器源码，可复用 |

复现命令：

```
PYTHONIOENCODING=utf-8 python convert.py <输入.md> -o <输出.html>
```

## 做法

`convert.py` 是一个手写的 Markdown → 带货 inline style 的 HTML 转换器，
不依赖任何第三方库（只用标准库 `re` / `html` / `html.parser`）。

支持：YAML frontmatter、`#`~`####` 标题、段落、粗体/斜体/行内代码/链接、
围栏代码块（带语言标签栏）、表格、`> [!NOTE|TIP|IMPORTANT|WARNING|CAUTION|DANGER]`
提示框、普通引用、有序/无序列表（两级）、`---` 分割线。

### 我假设的「微信公众号编辑器」行为

这些是设计的前提，不是实测结论（原因见下文「不确定的地方」）：

1. **粘贴时会剥掉 `<style>` 标签、`class`、`id`、`<script>`**，只保留 inline style。
   所以所有样式都写成 `style="..."`，没有一行外部 CSS。
2. **不保留 flex / grid / position**，所以正文里一个都没用，全部是普通 block 流向。
3. **`<section>` 是安全容器**（微信自己的模板就用 section），整篇正文包在一个
   `<section id="wx-article">` 里，粘贴后结构保留度最高。
4. **正文没有可靠的横向滚动条**，所以代码块用
   `white-space:pre-wrap` + `overflow-wrap:break-word`，长行在手机上自动折行，
   而不是靠左右拖动查看。
5. **`text-transform` 会被过滤**，所以代码块的语言名在 Python 里就转成大写
   （输出 `PYTHON` / `BASH`），不靠 CSS 转。
6. **`-webkit-font-smoothing`、`box-shadow`、`border-radius` 这类装饰属性
   大概率保留**，但都不承载信息，被剥掉也不影响可读性。
7. **`<a href>` 外链对未认证号会被清掉**，所以正文里的链接即使 href 没了，
   文字仍然可读（源文档里没有链接，只是防御性处理）。
8. **标题和摘要是编辑器里的独立输入框**，不在正文里。为了满足「只复制粘贴」
   这个需求，我把 frontmatter 的 `title` / `digest` 也渲染进了正文顶部，
   让粘贴出来的内容自成一篇；同时页面底部说明里提示了「填了编辑器标题栏
   就把正文顶部那行大标题删掉」。这一点是需求本身的两难，我选了
   「粘贴后立刻是完整文章」这一侧。

### 排版设计

frontmatter 里 `theme: accent`，我映射成一套蓝色强调色（`#0B63CE`）。

- 正文 16px / 行高 1.78，`#3D4A5C`，避免纯黑的生硬感
- 大标题 23px 粗体 + 作者署名行 + 圆角「摘要」卡片
- 二级标题：19px 粗体 + 底下一条 36×3px 的强调色短横，代替普通的整行下划线
- 提示框：浅色底 + 3px 左侧色条 + 圆角，`WARNING`/`CAUTION`/`DANGER` 额外加一个
  同色描边的文字徽章（注意 / 警告），因为颜色单独表达严重程度在手机上不够明确
- 代码块：深色 `#1B2430` 底，顶部一条语言标签栏
- 表格：强调色表头 + 斑马纹，`table-layout:fixed` 防止宽内容撑破，13px 字号
- 分隔线：三个小圆点

### 页面上的复制按钮

HTML 里带了一个固定在右上角的「复制到公众号」按钮，点一下用
`Range.selectNodeContents` 只选中 `#wx-article`，然后 `execCommand('copy')`。
它放在正文 `<section>` 外面，所以不会被选中、不会被粘进去。
`<script>` 粘到微信后会被剥掉，不影响正文。

## 自查

脚本 `main()` 里有两道自动检查，不通过就 `exit(1)`：

1. 正文里不能出现 `class=` / `<style` / `<script`
2. 用 `html.parser` 解析正文，**只要发现属性名里带空格、逗号、引号、冒号、
   括号或斜杠就报错** —— 这是「inline style 里的引号把属性提前闭合」的
   典型特征。浏览器遇到这种错误不报错，只是静默丢掉整条 style，
   肉眼很难发现，必须在生成阶段拦。

第 2 条不是预先想到的，是**写完之后真踩到了才补上的**：第一版
`font-family` 里写的是 `"Helvetica Neue"` 这种双引号，正好在
`style="..."` 双引号属性内部，把属性截断了，整条字体声明连带后面的
`font-size` 全部失效。现已全部改成单引号，并加了回归测试确认验证器
能抓到这一类问题。

另外顺手修掉两个：
- `join_lines` 一开始把「先用 CSV 验证」的中英文之间空格也删了，已改成
  只在「中↔中」之间删空格。
- NOTE 类提示框没有徽章，`None` 被 `%s` 直接渲染进了 HTML，
  已加 `>None<` 检测防止再犯。

最终产物验证结果：

```
正文无 class/id/style/script, 全部样式已 inline
属性结构合法, 无被引号截断的 inline style
```

结构核对：3 个正文段落、4 个二级标题（含原文的 `#` 一级标题，
在公众号语境下与 `##` 同级处理）、1 个表格 4 行、2 个代码块、
3 个提示框（1 NOTE + 1 WARNING + 1 DANGER），与源文件逐项对齐。

源文件里没有列表、普通引用、水平线，所以这三条路径我用一份临时测试
文档单独跑过，确认输出结构正确（两级项目符号、悬挂缩进、有序/无序都对）。

## 我不确定的地方

按重要性排序：

1. **没有做真实粘贴验证。** 这个环境里没有 mp.weixin.qq.com 的账号，
   集成浏览器也连不上（Pencil MCP 报 `transport not connected`），
   所以我**一次都没有在真机或真实编辑器里看过效果**。
   所有结论都是结构性的静态检查。上面的「微信行为假设」全部来自既有认知，
   没有一条是本次实测的。这是这次交付最大的缺口 —— 第一次真粘贴时
   请重点看这几处：代码块折行、表格列宽、提示框的圆角和边框。
2. **表格在手机上的挤压。** 三列表格在 ~340px 的实际正文宽度下，
   每列只有 90px 左右。「光合作用分两个阶段」这类内容会折成 2 行。
   能读，但不宽裕。如果要更好看，需要改内容而不是改样式
   （比如缩短示例文本）。微信编辑器还可能对表格重新处理，
   把 `table-layout:fixed` 丢掉，那样列宽会变成按内容自适应 —— 结果未知。
3. **`id="wx-article"` 会被剥掉**（大概率），剥掉不影响正文观感，
   只影响「在浏览器里打开源文件时复制按钮能不能工作」。
   按钮本身也无法在这个环境里点一次验证。
4. **列表的悬挂缩进用了 `text-indent:-1.2em`。** 项目符号和
   `1.` 是撑在负缩进里的，若出现两位数序号（`10.`）宽度会略超 1.2em，
   可能出现轻微错位。源文档没有列表，所以这条路径没有真实样本。
5. **字体栈基本会被微信覆盖。** `PingFang SC` / `Microsoft YaHei` 这串
   在正文里可能不生效，微信可能强制用它的默认字体。这不算问题，
   只是说明「字体控制」这一项其实不在我手里。
6. **字号是我按经验定的**（正文 16px）。微信正文的默认基准我没有实测数据，
   如果编辑器会缩放粘贴内容的字号比例，整体比例关系会变。
7. **frontmatter 的 `date: 2026-09-20`** 我当成发布日期直接渲染成了署名行。
   如果它其实是未来日期或者别的含义，署名行需要删掉。

## 如果重做

最大的改进是先想办法拿到一次真实的粘贴结果（真机截图或账号），
再用它反过来校准上面那 7 条假设 —— 现在整份产出建立在一组未经验证的前提上。
其次，表格和代码块是这种文章最容易在微信里翻车的地方，
应该优先做视觉验证，而不是像这次一样只能做结构验证。
